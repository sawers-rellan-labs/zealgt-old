# Handover: right-sized resource requests (time scaled by input size, per-task QOS routing), branch `simplify`, 2026-09-28

Base commit cbf905f. The user's requirement is "the right size plus a little wiggle room, never maxima for all tasks": large time or
memory requests wait longer, and backfill favours small jobs.

Mid-task, the coordinator extended the scope: adopt the Gate 3 projection's per-process requests (main checkout
`agent/20260928_145500_gate3_projection.md` §1b), route each task by its own time on `normal`, set queueSize 160, and document a
long head job. My own fit (§2) is kept as a cross-check.

## 1. What changed

- **`conf/hazel.config`** holds the per-process requests for both profiles. Every value is × `task.attempt`:

  | process | cpus | memory | time, attempt 1 (h, x = GiB of the task's own input files) |
  |---|---|---|---|
  | DEMUX | 6 bc1 / 4 | 2 GB | 1 h; **2 h for `bc2s3_batch1`** (fixed; routes to normal) |
  | MERGE_LANES | 4 | 1 GB | 30 min |
  | TRIMMOMATIC | **6** (was 8) | **2 GB** (was 8) | 0.1 + 0.105·x (raw merged pair `reads`) |
  | FASTQC | 2 | **3 GB** (was 4) | 0.1 + 0.032·x (trimmed pair `reads`) |
  | ALIGN_MARKDUP | 8 | `align_memory_gb` 48 (reserve 28 unchanged) | 0.25 + 0.323·x (trimmed pair `reads`) |
  | SAMTOOLS_STATS | 2 | **1 GB** (was 8) | 0.1 + 0.06·x (CRAM `input`) |
  | PICARD_COLLECTWGSMETRICS | **1** (was 2) | **5 GB** (was 8; -Xmx 4 GB) | 0.21 + 0.174·x (CRAM `bam`) |
  | MULTIQC | 1 | **2 GB** | 30 min |
  | DEMUX_QC / PROVENANCE / REGISTRY | 1 | **1 GB** | **10 min** |
  | MARKDUP_IMPORT | 4 | 12 GB | 30 min (unchanged, not in the projection) |

  - Size-scaled times are floored at **15 min** (my addition; the projection's intercepts of 6–15 min would otherwise be the
    floor) and rounded up to the minute.
  - The closure is `[reads].flatten().sum { f -> f.size() } / 2**30`. It handles both a two-file `BlankSeparatedList` and a
    single `TaskPath`, and was probed with sparse 20 GB files.
  - SAMTOOLS_STATS and Picard now have separate keys (they were one combined key).
- **`conf/normal.config`** has no selector any more. It sets only process-wide values:
  - `resourceLimits` time 24 h;
  - `queue` and `clusterOptions` closures on `task.time`: ≤ 105 min goes to `compute_partners` + `--qos=short`, otherwise to
    `compute` + `--qos=normal`. A task without a time goes to normal;
  - `executor.queueSize = 160`.

  hazel.config sets queue, clusterOptions and resourceLimits only process-wide, so the Gate 2 precedence trap cannot recur.
  `nextflow config -profile hazel,normal -flat` (`agent/20260929_001000_config_hazel_normal.txt`) shows no selector-level
  queue, clusterOptions or resourceLimits. Every process has a `withName` time, which beats base.config's label times.
- **`conf/short.config`** is unchanged. It caps everything at 1 h, all on compute_partners. `short` never loads normal.config,
  so it has no routing.
- **`scripts/check_resources.sh`** adds a **size probe**. A generated five-process stand-in script uses the modules' process
  and input names (`reads`, `input`, `bam`). It runs with `-c conf/hazel.config -c conf/<profile>.config` on sparse inputs
  for a 100 M and a 310 M pair sample (136 B per raw pair, 107 B per trimmed pair, 41 B of CRAM per pair). Its rows are
  `normal_100M`, `normal_310M`, `short_100M` and `short_310M`. It shows that a big input goes to `compute` and a small one to
  `compute_partners`. The fixture stub runs only reach the 15 min floor, so all of them route to short. The one exception is
  ALIGN_MARKDUP at 16 min: its 0.25 h intercept plus a few stub bytes, rounded up.
- **`tests/expected_resources.tsv`** is regenerated by `agent/20260928_235800_write_expected_resources.py`. That script
  computes the values independently of Nextflow.
- **`scripts/submit_head_job.sbatch`**: the header documents
  `sbatch --qos=normal --partition=compute --time=3-00:00:00 … -profile hazel,normal …`. Command-line options override the
  `#SBATCH` lines, so no flag was needed. The default stays short / 2 h, and ZG_REPO is kept.

## 5. Open points

1. **The QOS in clusterOptions is not in the trace.** The check verifies `queue` only. clusterOptions uses the identical
   `task.time <= 105.min` test in the same file (visible in `nextflow config`). A first normal run should confirm it with
   `sacct -o partition,qos`.
2. **Short-routed tasks and resourceLimits.** Short-routed tasks ask ≤ 1 h 45, under short's 2 h cap. `resourceLimits` on
   `normal` is 24 h for all tasks, so a retry can move a task to normal. That is intended.
3. **Size is read on the head node** at submission (`Path.size()` on /share, one stat per input file). This is cheap. A
   missing input would fail before the task anyway.
4. **Untested on hazel:**
   - TRIMMOMATIC at 6 cpus / 2 GB (the projection's risk 8): if wave 1 shows a > 20 % slowdown, go back to 8.
   - Picard at 1 cpu / 5 GB.
   - FASTQC at 3 GB: its heap is memory / cpus, 1.5 GB against a 0.74 GB peak.
   - The 15 min floor: a Gate 1 subsample run on `short` now asks 15 min where it asked 1 h. Fine at Gate 1 sizes; the retry
     doubles it.
5. **DEMUX is a fixed time, never size-scaled.** For batch 1 the staged inputs are the ~1.5 TB plate tars. The coordinator's
   batch-1 audit measured 12.3 µs/pair locally, i.e. ~0.5–1.5 h per lane at 4 cpus. So `bc2s3_batch1` gets 2 h × attempt,
   which `normal` routes to compute / normal; every other source gets 1 h. It is checked by a `<profile>_batch1` probe row.
   It is still unmeasured on hazel. DEMUX and TRIMMOMATIC module code is untouched.
   Low-pass batch-1 per-sample tasks sit at the 15 min floors, so they go to short QOS and backfill.
6. **The probe writes sparse files** of up to ~21 GB logical size under `agent/check_resources/<time>/probe/in`. They take no
   disk blocks on APFS or ext4, but a backup tool that ignores sparseness would see about 90 GB per check run. Those scratch
   dirs accumulate; remove them only with consent.
7. **`agent/20260928_232000_closure_test/`** holds sparse probe files (40 GB + 12 GB logical). They are scratch; remove them
   only with consent.
9. **Concurrent session in this worktree.** Another session had uncommitted edits in main.nf, workflows/cram.nf,
   subworkflows/local/{read_demultiplexing,read_trimming,utils_nfcore_zealgt_pipeline}, tests/, docs/PLAN_pipeline.md,
   docs/output.md and docs/usage.md. It committed them as 9f8aa95 during this task, and that commit also contains **my
   docs/usage.md hunk** (the Profiles and Resources lines): it staged the whole file. So my commit has no usage.md change.
   The check runs ran on the tree with their edits in it (same as 9f8aa95).
